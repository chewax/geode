## Phase Goal

**As a** persona que toma notas (no técnica), **I want to** que la bóveda se guarde sola cada cierto tiempo, sólo cuando algo cambió y sin gastar en IA, **so that** nunca pierdo trabajo aunque me olvide de guardar y sin ver jerga de git.

<objective>
Build the auto-snapshot engine end to end: a configurable cadence persisted like the existing `ai`/`github` settings, a main-process `setInterval` timer bound to the active vault, a single central `snapshotIfChanged(reason)` that commits only when content changed and never calls AI, and a new "Guardado automático" section in the Settings modal. After this plan the vault snapshots itself on the chosen cadence (Manual / 5 / 10 / 15 / 30 min, default 10 ON), producing commits labeled `"Instantánea automática — {fecha}"` only when there are real changes.

Purpose: This is the core capability of the phase (SNAP-01, SNAP-02, SNAP-04). It also introduces `snapshotIfChanged` and `restartSnapshotTimer`, the two symbols Plan 02 reuses for the safety snapshots (vault switch + quit). The change engine is reused verbatim from `git.ts` (`commit()` — content-hash vs HEAD, racy-safe, returns `null` on a clean tree), so an empty commit is structurally impossible and the racy-git landmine is never re-opened.

Output: new `SnapshotsConfig`/`SnapshotsApi` + `geode:snapshots-get/set` channels + preload bridge + `settings.snapshots` sub-object + `setSnapshotCadence`; main-process `snapshotMessage()`, `snapshotIfChanged()`, `restartSnapshotTimer()`, the two IPC handlers (with cadence validation), timer wiring into `vaultOpen`/`vaultSwitch`/`restoreLastVault`; and the Settings UI section. All additive; `npm run typecheck` and `npm run build` stay green.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → main IPC (`geode:snapshots-set`) | Renderer sends a `number \| null` cadence. Untrusted: a tampered/garbage value must not reach `setInterval`. |
| main-process timer → GitService/disk | The interval commits via `gitService.commit()`, which resolves inside the vault root (`resolveInside`) and writes atomically. No new file paths. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Denial of Service | `snapshots-set` handler → `setInterval` | mitigate | Validate `cadenceMinutes` against `null\|5\|10\|15\|30` in the handler; coerce anything else to `null` (manual) with a `console.warn` before persisting. A `0`/negative value can never reach `setInterval`, so no 0ms tight-loop. `[Security V5]` |
| T-04-02 | Denial of Service | Commit spam / unbounded history growth on an idle vault | accept | Inherent gate: `gitService.commit()` returns `null` on a clean tree (SNAP-02), so cadence ticks on an unchanged vault create zero commits. Spam is structurally impossible. |
| T-04-03 | Information Disclosure | Auto-snapshot marker message | accept | `snapshotMessage()` is a fixed template + local timestamp only — no user note content, no secrets. |
| T-04-04 | Tampering | Snapshot writing outside the vault root | accept | Already mitigated by `GitService`/`atomicWrite` (`resolveInside`); this plan adds no new file paths. |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | Zero new dependencies — reuses `electron` (`setInterval`), `isomorphic-git` (`commit()`), and in-repo `SettingsService`. Package Legitimacy Gate N/A (no install tasks). |
</threat_model>
